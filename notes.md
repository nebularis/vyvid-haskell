# Note register

**Unit type:** Register

A note says how to do something with a Haskell compiler index. Each one was measured or run, and its Evidence cell says what was run and on which version. A note holds for the versions it names and for the platform it was run on, until it is run again. A project may keep a register of the same type and name one of these rows in its Specialises column.

| ID | Tool | Claim | Problem shape | Evidence | Activity | Technology | Specialises | Overrides |

| NOTE-1 | ghc | **A `.hie` file starts with `HIE` and four digits of the GHC version that wrote it, as `HIE9103` for 9.10.3 and `HIE9124` for 9.12.4.** | Which GHC wrote a `.hie` file, and whether a tool can read it. The flag that makes ghc write one is in the Tools domain's note on `.hie` files. | One module compiled with `-fwrite-ide-info -hiedir=<dir> -c` under ghc 9.10.3 and again under 9.12.4, then the first bytes of each file read with `xxd`. They were `HIE9103` and `HIE9124`, each followed by the version text. Other versions were not tried. macOS arm64. | | | | |
| NOTE-2 | hiedb | **A `.hie` file holds the source of its module, and hiedb reads only a file written by the GHC it was built with. A file from another version stops it with a panic and leaves an empty database.** | A `.hie` file is moved to another machine or kept after a GHC upgrade, and an index of it fails or is empty. | `strings` on a one-module `.hie` printed the module's text, and `hiedb cat` printed it back. hiedb 0.8.0.0, built with ghc 9.10.3, indexed a file from 9.10.3 and exited 0. On a file from 9.12.4 it printed "hie file versions don't match", "Expected 9103 but got 9124", exited 1, and the database it had been given was a file of 106,496 bytes with no module in it. macOS arm64. | | | | |
| NOTE-3 | cabal | **A Hackage package built into the cabal store with no flag leaves no `.hie` file, so a dependency has none until it is built again with `-fwrite-ide-info`.** | An index of a project and its dependencies shows names called in a dependency and not where they are defined. | A cabal store of 144 entries for ghc 9.10.3, holding the dependencies of a project built with the flag set for the project's own packages only. `find` over the store found no `.hie` file. When the flag was then set for one Hackage package, its files were written to the `-hiedir` named and not into the store. cabal-install 3.16.1.0, ghc 9.10.3, macOS arm64. | | | | |
| NOTE-4 | cabal | **Setting `ghc-options: -fwrite-ide-info -hiedir=<dir>` for a package in `cabal.project.local` builds it again as a new store entry with a new unit id, and the old entry stays.** | A dependency is rebuilt for its `.hie` files and the unit id in an earlier index no longer matches the package. | One Hackage package was built twice, once before the setting and once after. The store held both entries, with different hashes in their names, and the `cabal-hash.txt` of the two differed by one line, the `ghc-options` line, which holds the `-hiedir` path. The index of the new `.hie` files carried the new unit id. A different path was not tried, and would be expected to give a third. cabal-install 3.16.1.0, ghc 9.10.3, macOS arm64. | | | | |
| NOTE-5 | hiedb | **In `refs`, a reference names the module that defines the name, not the facade module the referencing module imported it through.** | Who uses a function, when callers import a re-exporting module and the definition is elsewhere. | In an index of 60 modules, a module that imported only a re-exporting facade and referenced one of the facade's functions had a `refs` row whose `mod` was the module defining it, not the facade. The `imports` table of the caller listed the facade and not the defining module. One function was checked. hiedb 0.8.0.0, macOS arm64. | | | | |
| NOTE-6 | hiedb | **`hiedb -D <path>` on a path that holds no database creates an empty one and exits 0, so a mistyped path reads as no results.** | A query prints nothing and exits 0, and it is unclear whether the name is unused or the database is wrong. | `hiedb -D typo.db name-refs <name>` in a folder where `typo.db` did not exist exited 0 and printed nothing. `typo.db` was then a file of 106,496 bytes with 9 tables and no module. hiedb 0.8.0.0, macOS arm64. | | | | |
| NOTE-7 | hiedb | **With no `-D`, hiedb opens `default_99999103.hiedb` in `$XDG_DATA_HOME`, else `~/.local/share`. It creates the database empty there when the folder exists and fails when it does not.** | A command was run without `-D` and either wrote a database into the home folder or reported an error about a file never named. | With `HOME` pointing at an empty scratch folder, `hiedb name-refs <name>` exited 1 with "unable to open database file". | NOTE-8 | hiedb | **A name hiedb does not know gives no output and exit 0 from `name-refs`, and a message and exit 1 from `name-def` given a module.** | A misspelt name is read as having no callers. | In a database of one module, `name-refs` for a misspelt name exited 0 with no output, and for the right name printed three spans. `name-def <misspelt> <module>` printed "Couldn't find name" and exited 1. hiedb 0.8.0.0, macOS arm64. | | | | |
| NOTE-9 | sqlite3 | **An hiedb database is in WAL mode, so a read-only open of it in a folder that cannot be written fails, and `file:<path>?immutable=1` reads it but does not see what its `-wal` file holds.** | Reading an hiedb database without hiedb, from a read-only checkout or while another process holds it. | `pragma journal_mode` on a database hiedb wrote returned `wal`. In a separate Python test a table created and one row inserted in WAL mode, with the connection still open, were not seen through `immutable=1` ("no such table") and were through `mode=ro`.
